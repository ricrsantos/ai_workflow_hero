# Design: Browser Validation, Test Access, and Active Execution Budgets

Follows ADR-002 (feature vertical slices), ADR-003 (CLI deterministic; reasoning in Runtime), ADR-012/013 (store/engine boundaries), ADR-061 (Telegram daemon edge), ADR-080 (media facts), and ADR-103–106. Existing vertical-slice boundaries are kept; no architecture change beyond ADR-C17-002.

## D1 — `internal/testaccess` vertical slice (ADR-103)

New package owns: dotenv lexer/parser/serializer (blank lines, comments, unquoted, literal single-quoted, double-quoted with `\n \r \t \" \\` only; `$` literal; spaces/`#` preserved inside quotes; unsupported escapes and malformed quoting rejected with line/field diagnostics that never include values); user-ID validation `[a-z][a-z0-9_]*` with uppercase suffix derivation, duplicate-ID/key and ambiguous-normalization rejection; required-account usability check (non-empty login/password/profile); file read/write/reload with 0600, atomic replace, no residual backups; idempotent root-anchored `/.env.hero` gitignore insertion preserving content; manual-file validation (parser errors, owner/mode, git ignore/tracked status, symlink/unsafe-path refusal); stale-draft detection (loaded revision vs current; refuse stale save with Reload instruction); per-attempt credential snapshots. Never sources the file, never expands shell variables. Conversation-facing and TUI layers depend on this package; adapters never parse credentials. Secret values live only in `.env.hero` bytes and short-lived executor memory.

## D2 — Authentication executor and login recipe (ADR-103)

Approved contract clarification (2026-09-30): `planning_agent` creates `.workflow-hero/cycles/current/browser-plan.json` during Planning for each consuming application with browser validation. This is the shared non-secret recipe, coverage, and approved-method artifact consumed and validated by deterministic stage preparation before browser execution. Its application-specific values remain Planning-owned. Implementation defines its shared schema, loader, validation, and four-harness producer/consumer instructions; Browser UI/E2E agents use the planned contract. Credentials remain in project-root `.env.hero` and private executor memory.

`internal/testaccess` exposes a deterministic executor interface: input is a non-secret planned recipe (environment/base URL, approved-origin allow-list, login entry and form locators, protected verification target and expected role, selected user/profile, chosen execution method/tool/version, start/readiness and E2E commands, action/test timeouts, fixtures, and evidence paths) plus a private selected-account read; output is a sanitized preparation result (ok/blocked, verified role, affected coverage IDs, next action) with no secret values. The recipe schema is shared, while application-specific values are produced dynamically during Research/Planning for each consuming application. Hero does not hardcode application origins, routes, selectors, credentials, fixtures, or runner commands. For this cycle's tests, use only the synthetic local protected fixture with operator/admin roles; do not use real credentials or the user's Angular application.

For repeatable E2E, prefer an existing Playwright Test suite. For coding-agent browser control, prefer the official Playwright CLI with its official skill; if the harness cannot load skills, use the CLI's documented skills-less mode. Use MCP for specialized loops needing persistent browser state or iterative page inspection, or when verified CLI capability is insufficient. The skill is guidance for the CLI, not a separate browser executor. The minimum Playwright package baseline is 1.63.0, verified in the reference development environment on 2026-09-30. Planning validates the selected project/harness version and actual capability; QA does not install or upgrade tools. Missing or below-minimum tools block preparation. The executor establishes the isolated in-memory browser context subsequently used by the selected suite/CLI/MCP method. If the method cannot continue in that context, the integration blocks with configuration instructions instead of receiving passwords. Prompts, tool arguments, SQLite, YAML/snapshots, conversation logs, metrics, events, Telegram, command lines, diagnostics, and captures are covered by sentinel-secret tests. Trusted-harness disclosure: general-purpose privileged harnesses can technically read local files; apply harness permission policy where available and never claim 0600 is a sandbox (ADR-103).

Official Playwright guidance reviewed 2026-09-30: https://playwright.dev/docs/getting-started-cli and https://playwright.dev/docs/getting-started-mcp.

## D3 — Schema v16/v17 additive migrations (ADR-104, ADR-105, ADR-106)

The v16 migration remains the transactional, additive migration from v15: stage budget ledger (`stage_budgets`: stage key, consumed_ms, state active/waiting/blocked/expired/interrupted, pause/interruption reason, generation, updated_at), blocked/coverage records, and screenshot manifests. Existing rows are preserved and `hero.db` is never recreated; a real-SQLite v15 fixture covers prior operational state.

Implementation adds a separate transactional, additive v17 migration from v16 for traceable Planning coverage: `stage_coverage` gains requirement reference, screen/journey, evidence requirements, and optional responsive-reference widths; `stage_coverage_plans` records the approved non-secret browser-plan digest and approval time. Existing v16 coverage rows retain empty/default metadata and do not receive an invented plan snapshot. The engine snapshots the denominator and complete plan digest atomically before validation, rejects unapproved changes, and refreshes it only with explicit Planning approval. Managed config/report contracts remain described in their respective tasks; active-budget checkpoints remain 5 seconds and termination grace 15 seconds.

## D4 — Blocked reports and scheduler state (ADR-104)

`internal/cycle/reports` Browser UI/E2E contracts gain `blocked` plus validated preparation, blockers, coverage, and safe evidence references. A planned coverage denominator with mandatory-item accounting is validated before state mutation. Mixed validated reports persist genuine C15 findings/occurrences (identity, repro admission, owner, loop ceilings unchanged) together with blocker/coverage data in one transaction, set Blocked, and schedule no repair. `engine/store` persist operational Blocked/interrupted reason and budget state, exposed additively via cycle/status and Telegram. `/hero-continue` rechecks prerequisites from current configuration first; then genuine-finding repair and outstanding coverage gates apply. Preflight blocked before validation spends active time but no validation iteration. Invalid reports keep existing diagnostic/retry behavior within remaining budget. Only the scheduler transitions state or accepts findings/tasks; agents report observations.

## D5 — Active budget enforcement (ADR-105)

`engine/store` own the durable cumulative active wall-time budget per stage; the TUI owns execution generations, independent deadline scheduling, and async scoped cancellation with a fixed 15-second termination grace. Elapsed accrues once while any stage-owned work (execution, bounded preparation, scheduler-owned work) is active; paused only when none is active due to human credentials/questions/permissions/approval (a runnable sibling keeps the clock running); idle blocked/offline excluded; free chat excluded. Consumption is persisted at start/pause/resume/termination and every 5 seconds while active (fake-clock tested); restart charges the last persisted active checkpoint, marks interrupted, requires `/hero-continue`, never counts offline time, and never grants a fresh budget. Remaining time caps preparation/actions/tests/reconnects; zero balance requires explicit validated user budget increase. Expiry revokes generation acceptance before cancellation; completion and expiry share one serialized scheduler acceptance boundary requiring positive remaining time at acceptance. Late/expired/cancelled/interrupted results cannot close stages, accept tasks/findings, or start successors. Nested work is scoped to its parent; unsupported termination is disclosed and escalated. Progress warnings (60s without coverage progress, 30 repetitive events) and CheckHealth/watchdog stay passive; OpenCode patch diagnostics use safe identifiers/counts. This amends baseline PRD §5.4; it is not a watchdog modification. Constants: preparation default 120s total per attempt, max two attempts per prerequisite, warning thresholds 60s/30 events, checkpoint interval 5s, and termination grace 15s.

## D6 — Screenshots (ADR-106)

Capture belongs to browser execution; retrieval belongs to deterministic TUI control handlers reusing existing C14 media validation/cards/viewer (no inline terminal protocols). Each stage toggle (`screenshots.enabled`, default false, per Browser UI and browser E2E; HTTP-only E2E cannot enable) gates per-screen communication captures correlated with coverage/user/attempt; different attempts/roles never overwrite. Files land immutable under `.workflow-hero/cycles/current/screenshots/` with ready-set semantics (never show partial writes); manifest carries sanitized metadata only. Credential fill/submit suspends capture; sensitive-field/token masks apply; omission records an actionable reason; missing mandatory safe evidence blocks its item while optional delivery failure only warns. `/hero-screenshot` (latest/list/id/todos; `list`/`todos` reserved) is read-only, runs during streaming without harness dispatch, snapshots the ready set, and delivers bounded async batches with progress/partial-failure reporting. Telegram image edge extends the addressed IPC/outbound path: actual images only when project `always_send` is set and the addressed chat is paired/connected; queue jobs carry validated managed references plus safe captions; Bot API size/group limits verified in Planning (no hardcoded assumed limits); daemon mismatch/disconnect yields actionable warnings with local cards retained. Cycle evidence survives archive; archive resolves paths safely and never deletes screenshots with credential cleanup.

## D7 — Config and lifecycle wiring (FR-02, FR-04, FR-12)

Approved contract clarification (2026-09-30): the Test users opt-in is the persistent top-level `test_access.enabled` boolean in `workflow-config.yml`, default `false` when absent. Config and execution read the same managed setting; required login preparation blocks with enable instructions while it is disabled. The editor's session-only flag must be replaced by this persisted setting, with atomic YAML writes and execution guards. This config contains no credential values.

Config gains an opt-in Test users editor (scrollable add/edit/remove; stable ID, profile, login, masked password; Save/Discard/Cancel; reload on external change; read-only under existing execution guards) and per-stage Screenshots Off/On. Disabled setup with a required login-needing test blocks with enable instructions. Archive cleanup calls `testaccess` exact-path removal only after archive prerequisites succeed; refused/failed archive keeps the file; cleanup failure leaves archive pending with actionable retry; finish/cancel/upgrade/uninstall preserve; uninstall discloses retention. Install/upgrade provision root `.env.hero.example` placeholders without overwriting customized examples or application `.env`, and never create credential values or copy `.env.hero` into checksums/backups/snapshots/artifacts.

## D8 — Harness parity and help (PRD §6)

Planning/implementation apply typed reports, scheduler/storage/config, all four TUI harness prompt projections (Cursor, OpenCode, Codex, Claude), and help text together. Environment/tool absence supersedes the former missing-Playwright frontend-failure policy; no QA provisioning path; no silent HTTP fallback; HTTP mode stays explicit via `qa_end_to_end.use_playwright`. TUI keyboard shortcut for the screenshot collection is chosen after checking the keyboard guide for collisions, then listed in `/help` and the footer. No IDE execution or removal work.

## D9 — Lint/static baseline rule (user-approved 2026-10-01)

This replaces the former one-wave lint exception and applies to every remaining Implementation wave and to task-19. The `staticcheck ./...` (189) and `golangci-lint run` (149) diagnostics recorded in `verification-wave-1-lint-baseline.txt` pre-date C17, are out of scope for this change, and are tracked as Known Technical Debt in `context/current-state.md`. Lint/static acceptance is two exact commands (amended 2026-10-01; key-based comparison against the truncated golangci section of the baseline produced false positives, and pre-existing diagnostics in files C17 merely touched are out of scope): (1) `golangci-lint run --new-from-rev=a74db0f --max-issues-per-linter 0 --max-same-issues 0 ./...` exits 0, where `a74db0f` is the pre-C17 base commit; (2) `staticcheck ./...` reports no `file|message` key absent from the staticcheck section of the baseline. Baseline diagnostics never set `tests_passed` or `acceptance_gates.required_tests_passed` to false. `tests_passed` and `required_tests_passed` cover `go test ./...` plus the Verify commands of the IDs in `tasks_completed`; unfinished IDs are reported in `tasks_remaining`. All tests, builds, `go vet`, and race checks remain mandatory.

## D10 — Production call sites for preparation, capture, and delivery (user-approved 2026-10-01)

Hero does not own a browser process: the browser runs inside the stage agent's harness (Playwright Test, CLI, or MCP per D2). Hero's deterministic part is pre-dispatch admission and post-report ingestion. No new browser runtime is introduced.

- task-09 (preparation and method admission): in `startStageAgentSessions` (`internal/tui/stage_handoff.go`), before dispatching `browser_ui_validation` or `qa_end_to_end` agents, run `testaccess.Preparer.PreparePlan` as a `tea.Cmd` (never inside Update) with the remaining stage budget from the D5 ledger. The production `PreparationCapability`/`BrowserMethodAdmitter` live in `internal/testaccess`: service readiness is a bounded HTTP probe of the plan's base URL; method admission runs the plan-declared tool version command as a fixed argv (no shell) and compares it with the 1.63.0 minimum; harness capability comes from the selected harness descriptor. Decisions (user-approved 2026-10-01): (a) fixture entries that are project-relative paths are checked by the Preparer (exist, resolve inside the project, no symlink escape); label-only fixtures are confirmed by the dispatched stage session in its report `preparation` section; (b) a deliberately planned HTTP/API QA End-to-End (`use_playwright: false` and plan method `http`) skips Playwright/browser admission, keeps screenshots disabled, and checks only service readiness — it is never a silent fallback from a browser plan; (c) pre-dispatch preparation is local only (service readiness, tool version, harness capability, selected-account usability, fixtures); login and protected-role verification run in the dispatched stage session and are reported in the report `preparation` section already validated by the gate. No adapter-level browser API is added. A blocked result goes through the existing blocked path (`engine/blocked_handoff.go`, `SchedulerHandledBlocked`) and dispatches no agent; a ready result appends only the sanitized `BoundedPreparationResult` to the stage-agent assignment. Verify with fake clocks and a fake capability; no real browser or network.
- task-11 (post-assertion capture): the stage agent writes each post-assertion image to `.workflow-hero/cycles/current/screenshots/.staging/<stage>/<attempt>/` and references it in `coverage.items.evidence`. After the validation report decodes, the TUI handoff ingests each staged reference through `screenshots.Service.CapturePlannedEvidence` (mandatory evidence) or `Capture` (optional), using a staged-file `CaptureSource` that validates the image via the existing media checks, publishes it to the ready set, and removes the staging file. Agents never write into the ready set. Missing or invalid mandatory evidence blocks its coverage item; optional failures warn only. Credential-flow suppression stays a harness-prompt contract (task-16 projections); the ingester refuses staged files whose report item does not attest suppression.
- task-13 (automatic Telegram forwarding): keep the existing `beginScreenshotAutoWatch` hook (`internal/tui/stage_handoff.go`, `internal/tui/screenshot_watch.go`); newly ready manifests produced by the task-11 ingestion are forwarded through `telegramScreenshotDeliveryCmd` only when `always_send` is set and the addressed chat is connected, deduplicated by batch ID, with failures as warnings that keep local cards.

## Risks

- Bot API limits differ by account/method; verify before choosing batch sizes (task-13).
- Browser-method capability varies per project; Planning must declare a compatible method per project rather than a Hero-wide default (task-09).
- Privileged harnesses can read local files; the secret-free integration contract plus sentinel tests is the mitigation, not file modes (task-03).
